# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record, read against the target the issue names (version, platform, branch or commit) in the issue context and repo-facts block. | Passes if a stranger could recreate the setup: the report names the operating system, the language or runtime version, and the code version tested (commit, tag, release, or branch). Where the issue names a specific version or platform, the tested one matches it or the difference is explicitly called out. Fails if any of these is missing, or a mismatch with the issue's target goes unmentioned. | required |
| steps-followable | The repro report's steps, read in order from the stated starting state to the trigger, together with any reproduction details the issue itself provides. | Passes if a stranger starting from a fresh setup could reach the trigger without guessing: every action, input, and parameter needed (setup, install, configuration, exact input, options, and the triggering command or API call) is either written in the report, given in the issue and stated by the report as used, or covered by a repo doc the report points to. A script or file need not be pasted if its exact contents can be written directly from inputs and parameters the report or issue gives. Fails only if the reader must invent something: a missing input, an unstated option or command, or a referenced script whose contents cannot be rebuilt from what the report and issue give. The number of steps and their formatting do not matter. | required |
| behavior-matches | The report's artifacts (output excerpt, log, traceback, test result, screenshot), read against the specific behavior the issue describes (its error, failing assertion, wrong value, or symptom). | Passes if an artifact shows the issue's own behavior: the same error, assertion, wrong value, or symptom, produced by the trigger the issue names. For a cannot-reproduce, passes if an artifact shows a genuine attempt at the issue's trigger and its result, and the report states plainly any way its conditions may have differed from the issue's; an honest, evidenced cannot-reproduce passes even when the reporter is unsure they hit the exact conditions. Fails if the artifact shows a different error, a different code path, or a setup or install failure mistaken for the bug; if a reproduction is claimed over an artifact that shows something else; or if there is no artifact, only a description. | required |
| claims-supported | The report's stated outcome and any claims about cause or scope, read against the artifacts in the same report. | Passes if the report's main outcome is backed by an artifact in the report: "reproduced" only when the artifact shows the issue's behavior; "could not reproduce" only when the artifact shows the attempt and the report does not overstate it (it says what it did not test or what may have differed). One representative artifact can stand for repeated runs the report summarizes in prose. Supporting observations in prose, and hypotheses clearly hedged as guesses ("appears", "may", "I think"), are fine as long as nothing in the artifacts contradicts them. Fails if the report claims more than its artifacts show: "reproduced" over output of a different behavior, a root cause stated as fact without evidence, results claimed for versions or platforms the report says were not tested, or a cannot-reproduce presented as proof the bug does not exist. | required |
| conventions-respected | The repo-facts block's contribution policy (AI-use disclosure, comment or report templates, required information), read against both the claim comment and the repro report. | Passes if every requirement the policy states for comments or contributions is met by the comments; for example, if the policy requires disclosing AI assistance, at least one of the comments discloses it. Passes if the policy states no requirement. Fails if a stated requirement is not met, or if the policy bans AI-assisted contributions. | required |
| claim-specific | The claim comment, read against the issue context. | Passes if the claim names something specific to this issue (its symptom, error, failing test, file, or trigger) and says what the commenter will do next. Fails if it is boilerplate that could be pasted unchanged onto any issue ("Can I work on this?"). | required |
| no-overpromise | The claim comment and repro report. | Passes if neither comment promises a fix, a pull request, or a delivery date; promising investigation or reproduction is fine. | preferred |

## Verdict rule

Accept if every required check passes; reject if any required check fails.
Preferred checks never change the verdict.

Unclear handling: for env-recorded, steps-followable, behavior-matches,
claims-supported, and claim-specific, unclear counts as fail, because proof
that cannot be verified is not ready to post. For conventions-respected,
unclear counts as pass when the repo-facts block gives no contribution
policy, because silence is not a requirement.
