# Rubric: is this pull request ready to submit?

Every package counts as AI-assisted work. A shortfall the PR states openly
(a deviation from the plan, a step it could not run, a variant it leaves for
later) is honest work, and it passes the check it touches unless that check
says otherwise. Only a shortfall that is hidden or unexplained fails. "Less
than everything" is not a reason to hold a PR.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The diff's changed files and hunks, read against the plan's change list, its files list, its "not in scope" lines, and any deviation note (in the plan, or stated in the PR description). | Passes if every hunk in the diff is one of these: the fix the plan describes, a test for it, a doc or changelog entry for the changed behavior, something the repo's stated asks require (for example a changelog entry or a removed xfail marker), or a change a deviation note names with a reason. It must also deliver every step the plan commits to, unless the PR says plainly which step it dropped and why. Fails if any hunk is outside those (a refactor, a dependency bump, a rename, a rewrite of code the fix does not need, edits to a file the plan never named, anything the plan lists as not in scope) with no deviation note, or if a plan step is missing with no mention. The fix being correct does not save an unplanned hunk. | required |
| description-honest | Each factual claim in the PR title and description about what the change does, read against the diff and the test evidence. Look hardest at fidelity claims ("implements the plan exactly", "no other changes", "tests added", "changelog included") and at fix claims ("fixes X", "handles both cases"). | Passes if every claim about the change is true of the diff and the evidence: each file, test, entry, or behavior the description says is there is in the diff, and anything extra in the diff is mentioned. Fails if the description claims something the diff does not contain, says "nothing else changed" or "exactly the plan" while the diff has an unplanned hunk, describes a different change than the diff makes, or claims a fix the evidence does not show. Leaving out a minor detail is not a fail; saying something false is. | required |
| repro-rerun | The test-evidence section, read against the plan's test plan and the repro evidence. List each failure mode, repro step, and control the test plan names. | Passes if the plan's main repro is shown re-run on the branch with an observable after-result (an output line, an exit code, a value, a visible state) that matches the expected-after the plan states, AND every other failure mode, variant, or control the test plan names is either shown with its after-result or stated plainly as not run, with a reason. An after-result that says it matches a specific expected output the plan or issue writes out ("matches the issue's expected output byte for byte") is observable. For a control (a case that already worked and must keep working), naming it and saying it is unchanged is enough. A new test in the diff that asserts the fixed behavior counts for a failure mode only if its passing outcome is shown in the evidence. Fails if the evidence is missing or says "(none provided)", if the after-result is a feeling or a bare "works" / "fixed" / "looks right" with nothing a reader could check, if the after-result shown does not match what the plan expected, or if a failure mode the test plan names is silently missing from the evidence. | required |
| repo-checks-run | The test-evidence section and the description, read against the plan's test plan and the repo-facts block's stated checks (the suite, linters, CI, or checklist the template or contribution guide asks for). | Passes if the PR names the repo's own suite or checks it ran (a command, a test target, or CI) and shows the outcome (pass, a count, a green status), or plainly says it could not run them and why. Fails if the repo's checks or suite are never mentioned, or if a named check is shown failing and the PR does not explain the failure. | required |
| diff-clean | Every hunk in the diff and the commit list. | Passes if every added or changed line serves the change the PR is about. Fails if the diff carries any of: debug leftovers (`print`, `console.log`, `dbg!`, `fmt.Println` added for tracing, stray logging), commented-out code, leftover TODO or FIXME hacks the PR adds, unrelated files (editor or OS files, build output, unrelated lockfile churn, local config), or formatting-only or reshuffling changes (reflowed lines, reordered statements, style rewrites) to code the fix does not need to touch. A formatting change the repo's formatter forces on the lines the fix edits is fine. | required |
| template-and-policy | The repo-facts block's "pull requests" line (the PR template's sections and checklist) and "contribution policy" line (including any AI-use policy), read against the PR title, description, and commits. | Passes if the repo states no template, checklist, or policy asks. When it does, passes if every stated ask is met with real content: each template section is filled in (an honest "n/a" with a reason counts), each checklist item is answered truthfully, each required entry (changelog, issue reference, tests) is present, and, when the policy asks for AI-use disclosure, the PR discloses AI use. Fails if a stated section or checklist is missing, left as the template's placeholder, or answered falsely; if a required entry is missing with no reason; if AI use goes undisclosed where the policy asks for disclosure; or if the policy bans AI-assisted contributions. | required |
| thread-engaged | The thread highlights: comments by OWNER, MEMBER, COLLABORATOR, or maintainer accounts, and any linked or open PRs, read against the PR description and the diff. | Passes if the thread has no maintainer direction and no other PR. When it does (a requested approach, a ruling, a request for a test or a specific behavior, an existing PR on the same fix), passes if the PR follows it or the description names it and says why it differs. Fails if the PR goes against an explicit maintainer direction, or duplicates an open PR, without saying so. | required |
| title-specific | The PR title. | Passes if the title says what the change does in terms a reviewer can check against the diff (for example "Reject --threads values above a sane cap instead of panicking"). | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check fails.
Preferred checks are reported but never change the verdict.

Unclear handling: unclear counts as fail for every required check, because a
PR whose readiness cannot be verified from the package is not ready to
submit. Two exceptions, because silence is not a requirement: for
template-and-policy, unclear counts as pass when the repo-facts block states
no template, checklist, or policy; for thread-engaged, unclear counts as pass
when the thread highlights hold no maintainer comment and no PR.
