# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded | The plan's stated cause (its diagnosis, or the "why" behind its change), read against every step, timing, and control run in the repro-evidence block, and against any diagnosis the thread highlights offer. | Passes if the stated cause explains what the repro evidence shows and nothing in the repro evidence rules it out: every control run, comparison, or variant the repro reports (for example "same input without flag X works", "with colors off it is instant", "the value is already wrong at step 4") is consistent with the cause the plan names. A cause taken from the thread or a maintainer passes only if the repro evidence is also consistent with it. A control the plan explicitly addresses with an explanation that nothing in the repro contradicts counts as consistent, even if that explanation is not yet proven; the plan does not have to prove its cause, only not be ruled out by its own evidence. Fails if any repro step or control contradicts the cause (the plan blames a component the evidence shows behaving correctly, or a stage the evidence shows the fault already happened before), if the plan ignores the repro's evidence and adopts a cause it does not support, or if the plan names no cause at all. Confidence, polish, and length do not count toward passing. | required |
| scope-bounded | The plan's change list and its in-scope / not-in-scope statements, read against the behavior the issue reports and the repro reproduces. | Passes if every change the plan commits to is needed to fix the reproduced behavior: the fix itself, tests for it, docs for the changed behavior, and closely related variants that the same fix covers. Explicitly deferring larger work ("not in scope: X, because Y") is good scoping, even when the deferred work is arguably part of the issue. Fails if the plan also commits to work the issue did not ask for: refactors or rewrites of surrounding code, dependency upgrades or migrations, new options, settings, or features, redesigns, UI rework, CI or test-harness changes, or "while I'm in the area" cleanups, even when the core fix inside it is correct. | required |
| executable | The plan's approach and the files, functions, or code areas it names. | Passes if a stranger could start the work without asking the author anything: the plan names where the change goes (a file, function, module, or clearly identified code site) and commits to one approach. Naming the module and the code path (for example "the reattach path in the server's session connection handling") is enough when the approach is fixed; leaving the exact function name to be pinned during the build does not fail this check. Fails if the location is "somewhere" or unnamed, if the approach is still a choice left open ("upstream or vendored, whichever is easier", "gocui? tcell? not sure"), or if the plan is an investigation ("poke around", "profile and see") rather than a change. | required |
| test-decisive | The plan's test plan, read against the repro-evidence block's steps and its expected-vs-actual result. | Passes if the test names an observable outcome that would be different if the fix did not work: re-running the repro steps with the expected result stated (an exit code, a value, an output line, a visible change at a named step), or a named regression test that asserts the fixed behavior. Running the wider suite in addition is fine. Fails if the only test is "run the full suite" or "make sure nothing regresses", or if the outcome is a feeling ("should feel fast", "works", "nothing feels broken") with nothing a reader could check. | required |
| thread-engaged | The plan and plan comment, read against the thread highlights: comments from OWNER, MEMBER, COLLABORATOR, or maintainer accounts, and any linked or open PRs mentioned. | Passes if the thread has no maintainer direction or prior-art PR. When it does (a maintainer's diagnosis, a requested approach, a request for testing, a ruling such as "working as intended", or an existing PR), passes if the plan or the comment acknowledges it and either follows it or says why it diverges. Fails if the comment and plan ignore an explicit maintainer direction or an open PR on the same fix, for example proposing a different change or a workaround without mentioning what the maintainer asked for. | required |
| conventions-met | The repo-facts block's contribution policy (AI-use rules, comment rules, required information), read against the plan comment. Treat every package as AI-assisted work. | Passes if the policy states no requirement for comments or contributions. When it does, passes if the plan comment meets every stated requirement: if the policy requires disclosing AI use, the comment discloses it; if the policy requires comments to be human-written, the comment does not present itself as AI-generated and reads in the author's own words. Fails if a stated requirement is not met, or if the policy bans AI-assisted contributions. | required |
| unknowns-stated | The plan's claims about cause, coverage, and risk, and the plan comment, read against what the repro evidence actually tested. | Passes if anything the plan has not verified (an untested platform, a guessed side effect, a variant it defers) is stated as unknown or deferred rather than claimed as fact. | preferred |
| no-overpromise | The plan comment. | Passes if the comment does not promise a delivery date or a timeline; stating the plan and that a PR will follow is fine. | preferred |

## Verdict rule

Accept if every required check passes; reject if any required check fails.
Preferred checks never change the verdict.

Unclear handling: for cause-grounded, scope-bounded, executable, and
test-decisive, unclear counts as fail, because a plan you cannot verify from
the package is not ready to build from. For thread-engaged, unclear counts as
pass when the thread highlights contain no maintainer comment and no PR, and
for conventions-met, unclear counts as pass when the repo-facts block states
no contribution policy, because silence is not a requirement.
